# 10k 历史评测的统计口径

两轮为 AMD 云端 BF16/use_length=25 与 FP32/use_length=50，各50个clean、50个randomized配置，目标各10次。根据每个 `Success rate:` 行恢复真实policy回合并核对累计次数连续性，实际各913回合。

- BF16/25：clean 274/478，randomized 131/435，合计405/913。
- FP32/50：clean 242/478，randomized 114/435，合计356/913。
- 每轮38个配置不足10回合；clean缺22，randomized缺65，共87。
- `Final success rate` 固定分母/10不能证明完成10回合；`episode_info.task_success`是专家信息，不能当policy成功。

已有百分比用于排查，尚不满足正式50×2×100回合评测。场景/专家跳过也可能带来选择偏差。两轮同时改了精度与步长，不能把差值解释为FP32单独更差，或把单任务少量样本差值当稳定结论。

`actual_task_results.csv` 每行是一个task/setting配置，分别列真实成功数、回合数、成功率与耗时。Excel对照表还包含逐回合与训练精度短测页；短测从基座开始，是可运行性检查，不是10k长训loss曲线，也不是优化器性能证据。

历史全量评测没有保存动作向量或视频，不能从这些日志恢复预测动作曲线。完整10k长训逐步loss日志目前未随备份保存，因此这里不提供凭截图重建的训练/验证loss曲线。

本次新导出包保留DCP中的FP32参数，逐张量值将校验。历史云端导出路径可能曾采用上游默认BF16保存，再以FP32计算加载；新包的存储数值与那个中间格式不能未经校验就称为完全相同。发布的历史表格明确对应当时运行记录，新包仍需匹配环境的闭环复测。

`scripts/archive/analyze_cloud_eval_comparison.py` 是原统计工具，输入为两轮完整原日志目录。`eval_actual_episode_wrapper.py` 是后来用于诊断的改进：在内存中调整停止条件、记录实际policy结果并固定逐seed指令随机数，包含版本锚点检查。它未用于修改上述历史结果，其正式评测适用性需要对照赛事规则确认。
